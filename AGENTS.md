# LotPulse: notes for contributors and coding agents

## Stack

- TanStack Start (React 19, file-based routing in `src/routes/`), Vite 8, Tailwind CSS 4, Nitro for the server build.
- Package manager: Bun (`bun.lock`). npm works too.
- `src/routeTree.gen.ts` is generated by the router plugin. Don't edit it by hand.

## Production data

Real students' scout names (`public.profiles`) and reports (`public.reports`) live in the
production Supabase project. Keep them intact:

- Never write SQL that removes or rewrites existing rows: no `DROP TABLE`, `TRUNCATE`,
  `DELETE FROM`, `DROP COLUMN`, lossy column type changes or bulk `UPDATE`s. Dropping and
  recreating views, policies, functions and triggers is fine.
- Migrations only add things. New `CHECK` constraints on existing tables use `NOT VALID`.
- Never run `supabase db push`, `supabase db reset --linked` or anything else against the linked
  project. The owner applies `supabase/setup.sql` by hand in the SQL Editor after review.
- If a task seems to need changing existing data, stop and ask the owner first.

## Application rules

- **Everything shown comes from real reports** in Supabase (`src/lib/supabase.ts`, `src/lib/live.ts`), kept live with Realtime. Without credentials the app shows no reports and refuses to send any. Don't add simulated data, forecasts or "predictive" wording.
- Lot risk is the number of reports in the last 2 hours (0 clear, 1 caution, 2+ high; `riskFor` in `src/lib/lots.ts`). Clout is 25 points per report, counted by the database.
- Database changes go in a new file under `supabase/migrations/` (never edit an applied one). Security lives in the database: RLS policies (public reads of the last 24 hours, insert-only as yourself, no client updates or deletes except `delete_my_data()`, which only removes the caller's own reports and account) plus least-privilege grants (the API roles hold no update or delete privileges) and the `guard_report` trigger (server timestamps and reporter, 5-minute per-lot cooldown, 6 per hour). `src/test/database.test.ts` runs every migration in PGlite, so extend it with each change. After adding a migration run `bun run db:setup-sql` to regenerate `supabase/setup.sql` (a test fails if it is stale).
- Reports only ever contain the lot, the time and a self-chosen scout name. Don't add photos, free text or anything that identifies officers or students.
- `src/lib/lots.ts` is the single source of truth for lot metadata, positions and the risk rule. The map and dashboard read from it.
- Visual tokens (colors, threat tones, radii) live in `src/styles.css`. Reusable UI belongs in `src/components/`.
- The campus map uses Leaflet. It uses OpenStreetMap tiles (darkened via CSS) and Esri satellite; if those fail and `VITE_MAPTILER_KEY` is set, it switches to MapTiler (light streets under the same CSS darkening, plus satellite, with the required MapTiler/OSM attribution). Any new tile host must be added to the CSP `img-src` in `vite.config.ts`. It only renders on the client.

## Checks

Run `bun run check` (typecheck, lint, tests) and `bun run build` before pushing.
